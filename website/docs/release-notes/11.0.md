# 11.0 release notes

InfoCarrier.Core 11.0.0 brings Entity Framework Core 11, progressive query results, and separate
client and server configuration with named endpoints.

The release requires .NET 11 and Entity Framework Core 11.
For an existing 10.3 application, review the [breaking changes](#breaking-changes) and
[upgrade guide](../upgrades/from-10-to-11.md) before updating.

## Entity Framework Core 11

Use `FullJoin` to include unmatched rows from either query source. Frozen sets can supply collection
values for server-side filters. Both paths are verified with SQLite; other server providers apply
their own translation rules.

See [full joins](../applications/querying.md#join-both-sets-including-unmatched-rows) and
[frozen-set filters](../applications/querying.md#filter-with-a-frozen-set) for examples.
[#283](https://github.com/azabluda/InfoCarrier.Core/pull/283)

## Configure clients and servers by role

Use `AddInfoCarrierClient` to configure a client and `AddInfoCarrierServer<TContext>` to configure
a server. Use `UseInfoCarrier` to connect a context to the configured client.

Put settings that must agree on both sides in a shared method. Call it through `ConfigureShared`
on each side. These settings include types, anonymous object shapes, value mappers, and SQL permission.

Give registrations names when an application needs several clients or server endpoints with different
settings. A server endpoint can select its configuration by name, server builder, or unique context type.

See [client configuration](../applications/configuration/client.md) and
[server configuration](../applications/configuration/server.md).
[#253](https://github.com/azabluda/InfoCarrier.Core/pull/253),
[#255](https://github.com/azabluda/InfoCarrier.Core/pull/255),
[#256](https://github.com/azabluda/InfoCarrier.Core/pull/256)

## Receive query rows progressively

Asynchronous queries without change tracking can return rows before the server finishes the query.
Tracked queries and operations returning one result still wait for buffered results.

This includes concatenated queries whose parts construct results on the client and can be processed
independently. `Skip(n)` and `Take(n)` can remain incremental after a client projection; range paging such
as `Take(1..3)` can require buffering.

Disposing the enumeration early cancels the response. A later error or response-size limit can
stop the query after you have received some rows.

See [streaming results](../applications/streaming.md).
[#244](https://github.com/azabluda/InfoCarrier.Core/pull/244),
[#245](https://github.com/azabluda/InfoCarrier.Core/pull/245),
[#256](https://github.com/azabluda/InfoCarrier.Core/pull/256),
[#291](https://github.com/azabluda/InfoCarrier.Core/pull/291)

## Document queries and saves

Updates to an owned object now apply the owner's returned concurrency value even when none of the
owner's own properties changed. Replacing or reordering owned collection elements preserves the
collection order sent to the server and applies generated element keys to the matching tracked objects.
Deferred acceptance with `SaveChanges(false)` retains these values until `AcceptAllChanges()`.

Key generation follows the server provider. Client temporary keys do not enable generation for a
server key that the provider does not generate. Returned keys and dependent foreign keys are updated together.

Dictionary results declared through `IDictionary<TKey, TValue>` or `IReadOnlyDictionary<TKey, TValue>`
are rebuilt as compatible dictionaries. Registered provider query methods returning `Task<T>` can
execute on the server, subject to that provider's translation and execution rules.

These paths are verified with the Entity Framework Core 11 Cosmos provider and independent controls.
MongoDB is not validated with this release. Cosmos retains its own partition, transaction, and
asynchronous execution requirements.

See [document-store configuration](../applications/configuration/document-stores.md),
[generated values](../applications/saving.md#store-generated-values-come-back), and
[value mappers](../extending/value-mappers.md).
[#287](https://github.com/azabluda/InfoCarrier.Core/pull/287)

## Synchronous operations and custom components

Synchronous calls now use synchronous transport and server execution.
Asynchronous calls keep their asynchronous path. An asynchronous-only backend can still refuse
synchronous operations.
Custom transports must implement both `Send` and `SendAsync`; custom clients and servers must
also implement their synchronous operation members.
[#251](https://github.com/azabluda/InfoCarrier.Core/pull/251)

Use `ReplaceService` on a client or server builder to replace supported transports, serializers,
clients, servers, or server pipelines. Replacements keep that registration's settings and service
lifetime. Measurements distinguish individual client and server registrations.

See [custom components](../extending/services.md).
[#256](https://github.com/azabluda/InfoCarrier.Core/pull/256)

`InfoCarrierTypeMappingSource` was removed. Custom subclasses must use
`InfoCarrier.Core.Relational.InfoCarrierRelationalTypeMappingSource` and its relational dependencies.
Ordinary application registration needs no mapping-source replacement.
See [custom component migration](../upgrades/from-10-to-11.md#rebuild-custom-components).
[#291](https://github.com/azabluda/InfoCarrier.Core/pull/291)

`ServerLogCapture.Begin` is now an instance method. Query-split event data no longer exposes
`UnregisteredKeyTypes`, and the old count-only query-split logging overload was removed.
Rebuild custom logging integrations and expression/value-mapper implementations against the current contracts.
Shared configuration builder methods also changed from instance methods to extension methods,
which requires rebuilding compiled callers even when their source is unchanged.
[#247](https://github.com/azabluda/InfoCarrier.Core/pull/247),
[#252](https://github.com/azabluda/InfoCarrier.Core/pull/252),
[#256](https://github.com/azabluda/InfoCarrier.Core/pull/256),
[#275](https://github.com/azabluda/InfoCarrier.Core/pull/275)

## Breaking changes

| Area | Required action |
|---|---|
| Runtime and framework | Move both applications and shared projects to .NET 11 and Entity Framework Core 11. |
| Configuration APIs | Replace `AddInfoCarrier`, the old options builder, and separate policy registrations with client/server role configuration. |
| Extra query types and anonymous shapes | Register types and structures needed by server execution on both sides. Missing registration no longer permits implicit local grouping, joins, or comparisons. |
| Local query execution | Rewrite operators that cannot run on the server, or put `AsEnumerable` before intentional local work. This includes filtering, ordering, grouping, joins, distinctness, set operations, and equality. |
| Client/server messages | Upgrade both applications together. Protocol 4 changes query and buffered-result payloads; format 3 conversion does not provide version 10 package support. |
| Custom transports, clients, and servers | Implement the synchronous members and rebuild against the current interfaces. Update custom serializers for the changed payloads. |
| Streamed results | Handle partial results and errors after rows arrive. Dispose enumerations when stopping early. |
| Client database setup | Move `EnsureCreated`, `EnsureDeleted`, and `CanConnect` to the server; client calls now fail. |
| Logging and provider extensions | Update static log-capture calls, query-split handlers, removed provider classes, and changed constructor signatures. |
| Compiled application libraries | Rebuild shared configuration and custom components, even when their source calls still compile unchanged. |

The registration change does not ban every unregistered result type or every anonymous `Select`.
Model types remain available automatically. Supported final client projections and safe internal
query rewrites remain supported. The stricter rule prevents missing registrations from silently
moving row selection, grouping, joins, or equality to the client.
See [type and shape migration](../upgrades/from-10-to-11.md#register-types-and-anonymous-shapes-used-by-server-execution).

## Choose local query execution explicitly

Queries that previously grouped, joined, or compared downloaded rows because a type was unregistered
can now throw `InvalidOperationException` before database execution. The same rule covers implicit
local filtering, ordering, distinctness, set operations, and equality comparisons.
Supported final result construction can still run on the client. Rewrites that keep operations
on the server remain supported.

Register additional named types with `AddAllowedTypes` and anonymous structures with `AddAnonymousShapes`
on both sides when the server needs them. Prefer one shared method applied through `ConfigureShared`.
Registration allows those values to cross the connection. The database provider must still
understand the query.

To choose local execution, put `AsEnumerable` before the local operation.
Filter and select the needed data on the server first to avoid downloading unnecessary rows.

See [query execution](../applications/querying.md#keys-of-your-own-types).
[#275](https://github.com/azabluda/InfoCarrier.Core/pull/275)

## Run database setup on the server

Client calls to `EnsureCreated`, `EnsureDeleted`, and `CanConnect` now fail.
Previously, they reported success without checking a database.
Create or delete the database, and check its connectivity, through the server's database context.
[#248](https://github.com/azabluda/InfoCarrier.Core/pull/248)

## Client and server compatibility

Version 11 does not support version 10 clients. Version 11.0 supports 11.0 clients only.
Later version 11 minor releases follow the policy of supporting the current and previous minor release.

The message format is now version 4. Conversion from format 3 is also implemented.
Accepting an older message format does not mean supporting every package that used it.
Tests with development clients do not prove compatibility with published older packages.

An unsupported protocol raises `InfoCarrierProtocolException`, which is separate from a connection failure.

Custom serializers now handle query contents and buffered result data.
Streamed messages still use the fixed JSON format.

See [compatibility](../reference/compatibility.md).
