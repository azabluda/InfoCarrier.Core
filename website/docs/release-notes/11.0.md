# 11.0 release notes

InfoCarrier.Core 11.0 is an unreleased development version. These draft notes describe changes
since 10.3. They do not describe the packages currently available on nuget.org.

## Entity Framework Core 11

Adoption is pending. The development branch still uses Entity Framework Core 10.

## Configure clients and servers by role

Use `AddInfoCarrierClient` to configure a client and `AddInfoCarrierServer<TContext>` to
configure a server. Use `UseInfoCarrier` to connect a context to the configured client.

Put settings that must agree on both sides in a shared method. Call it through `ConfigureShared`
on each side. These settings include types, anonymous object shapes, value mappers, and SQL permission.

Give registrations names when an application needs several clients or server endpoints with different
settings. A server endpoint can select its configuration by name, server builder, or unique context type.

See [client configuration](../applications/configuration/client.md) and
[server configuration](../applications/configuration/server.md).
[#253](https://github.com/azabluda/InfoCarrier.Core/pull/253),
[#255](https://github.com/azabluda/InfoCarrier.Core/pull/255),
[#256](https://github.com/azabluda/InfoCarrier.Core/pull/256)

## Choose local query execution explicitly

If a filter cannot run on the server, InfoCarrier now refuses it instead of silently filtering
downloaded rows. This also applies to ordering, grouping, joins, and equality comparisons.
Supported final result construction can still run on the client. Rewrites that keep operations
on the server remain supported.

Register shared types or anonymous shapes on both sides when the server needs them.
Registration allows those values to cross the connection. The database provider must still
understand the query.

To choose local execution, put `AsEnumerable` before the local operation.
Filter and select the needed data on the server first to avoid downloading unnecessary rows.

See [query execution](../applications/querying.md#keys-of-your-own-types).
[#275](https://github.com/azabluda/InfoCarrier.Core/pull/275)

## Receive query rows progressively

Asynchronous queries without change tracking can return rows before the server finishes the query.
Tracked queries and operations returning one result still wait for buffered results.

Disposing the enumeration early cancels the response. A later error or response-size limit can
stop the query after you have received some rows.

See [streaming results](../applications/streaming.md).
[#244](https://github.com/azabluda/InfoCarrier.Core/pull/244),
[#245](https://github.com/azabluda/InfoCarrier.Core/pull/245),
[#256](https://github.com/azabluda/InfoCarrier.Core/pull/256)

## Synchronous operations and custom components

Custom transports must now implement both `Send` and `SendAsync`.
Built-in synchronous calls use synchronous execution.
[#251](https://github.com/azabluda/InfoCarrier.Core/pull/251)

Use `ReplaceService` on a client or server builder to replace supported transports, serializers,
clients, servers, or server pipelines. Replacements keep that registration's settings and service
lifetime. Measurements distinguish individual client and server registrations.

See [custom components](../extending/services.md).
[#256](https://github.com/azabluda/InfoCarrier.Core/pull/256)

## Run database setup on the server

Client calls to `EnsureCreated`, `EnsureDeleted`, and `CanConnect` now fail.
Previously, they reported success without checking a database.
Create or delete the database, and check its connectivity, through the server's database context.
[#248](https://github.com/azabluda/InfoCarrier.Core/pull/248)

## Client and server compatibility

Version 11 does not support version 10 clients. Version 11.0 supports 11.0 clients only.
Later version 11 minor releases follow the policy of supporting the current and previous minor release.

The message format is now version 4. Conversion from format 3 is also implemented.
Accepting an older message format does not mean supporting every package that used it.
Tests with development clients do not prove compatibility with published older packages.

An unsupported protocol raises `InfoCarrierProtocolException`, which is separate from a connection failure.

Custom serializers now handle query contents and buffered result data.
Streamed messages still use the fixed JSON format.

See [compatibility](../reference/compatibility.md).
