# InfoCarrier.Core 10.0.0-preview.1

**A ground-up rewrite for EF Core 10.** This shares its name and its idea with
InfoCarrier.Core 1.0–3.1 and almost nothing else: the expression serializer, the wire
format, the client/server split and the security model are all new code.

Use the full power of Entity Framework Core in a client application that has no database —
LINQ, change tracking, the identity map, navigation fix-up, lazy loading, transactions —
with no connection string and no database driver. Queries and units of work travel to your
application server and run there against the real database.

> ### ⚠️ This release is not backward compatible with 3.1
>
> It is not an upgrade. Existing code will **not** compile against it, and that is
> deliberate rather than accidental — see [Upgrading from 3.1](#upgrading-from-31) below.

---

## ⚠️ Installing — you must name the version

`InfoCarrier.Core` has been on nuget.org since 1.0, and its newest **stable** release is
`3.1.1`. NuGet prefers a stable release over a prerelease, so:

```bash
dotnet add package InfoCarrier.Core                              # installs 3.1.1 — NOT this
dotnet add package InfoCarrier.Core --version 10.0.0-preview.1   # correct
dotnet add package InfoCarrier.Core --prerelease                 # also correct
```

It does not fail and it does not warn. This stays true until a stable `10.x` ships.

Two packages now:

| Package | Reference it from |
|---|---|
| `InfoCarrier.Core` | your **client**, and your **server** |
| `InfoCarrier.Core.AspNetCore` | your **server** only — `app.MapInfoCarrier()` |

## What is new since 3.1

### The platform

| | 3.1.1 (2021) | 10.0.0-preview.1 |
|---|---|---|
| Target framework | `netstandard2.0` | `net10.0` |
| EF Core | 3.1.3 | 10.0 |
| Dependencies | **Remote.Linq** (+ Aqua) | none beyond `Microsoft.EntityFrameworkCore` |
| Packages | one | two, split on the only line that costs anything |

### No Remote.Linq or Aqua

The expression serializer is in-tree and purpose-built. That is what makes the wire format,
its type allowlist and its trimming story ours to reason about — and it removes a
dependency tree from every client.

### A transport now ships

3.1 shipped **none** — you wrote your own. `HttpInfoCarrierTransport` is now in the box, and
`app.MapInfoCarrier()` is one line on the server. `IInfoCarrierTransport` is a single method,
so gRPC, a message bus or an in-process call remain a small class.

### A stated, tested security boundary

Your server executes an expression tree that arrived over the network. 3.1 had nothing to say
about that. This release has a default-deny allowlist over node kinds, types and methods; loads
no assembly to satisfy a payload; blocks the reflection entry points that turn a resolved
`Type` into a call; bounds the payload size before parsing; and ships a written review that
includes the weaknesses **accepted rather than solved**.

### Capabilities that did not exist in the EF Core 3.1 era

- **Complex types**
- **JSON-mapped owned collections**
- **`ExecuteUpdate` / `ExecuteDelete`**
- **Compiled models**
- **Many-to-many without an explicit join entity**
- **Savepoints** — 3.1 had begin/commit/rollback only
- **Spatial without data loss** — Z and M ordinates survive the round trip, which 3.1's
  GeoJSON form did not preserve
- **Blazor WebAssembly**, published **trimmed**, and verified by driving the real app

### An async-first client contract

3.1's `IInfoCarrierClient` carried sync and async pairs. This one is async throughout.

## How it is verified

This provider inherits **Microsoft's own EF Core specification suite** — the same suite EF
Core's SQL Server, SQLite and InMemory providers run:

```
Total tests: 22658, Passed: 22472, Failed: 9, Skipped: 177
```

The nine failures are known, classified, and **gated in CI so the number cannot grow
unnoticed**. They amount to one unsupported scenario, one query to treat with caution, and a
few differences that are not defects — two of which are queries this provider *answers* that
other EF Core providers reject.

Skipping a test to make the suite green is forbidden in this repository; a red test is
information.

**Read [the limitations page](https://azabluda.github.io/InfoCarrier.Core/limitations/)
before adopting.** It lists every scenario in that suite which does not behave the way a
normal EF Core provider behaves, with a worked example for each.

## Upgrading from 3.1

**Your `DbContext` and your entity classes are unchanged.** Everything around them moves.

| | 3.1.1 | 10.0.0-preview.1 |
|---|---|---|
| Client wiring | `UseInfoCarrierClient(client)` | `UseInfoCarrier(client)` |
| Transport | yours to write | `HttpInfoCarrierTransport`, or yours |
| Server endpoint | yours to write | `app.MapInfoCarrier()` |
| `IInfoCarrierClient` | sync + async pairs | async only, different shape |
| `IInfoCarrierServer` | different shape | — |
| `IInfoCarrierValueMapper` | different shape | — |

The three interfaces **kept their names and changed their shapes**. That is intentional: an
existing implementation fails to compile rather than compiling and misbehaving.

The four lines that replace your old client wiring:

```csharp
var serializer = new SystemTextJsonInfoCarrierSerializer();
using var http = new HttpClient { BaseAddress = new Uri("https://your-app-server") };
var client = new TransportInfoCarrierClient(new HttpInfoCarrierTransport(http, serializer), serializer);

var options = new DbContextOptionsBuilder<ShopContext>().UseInfoCarrier(client).Options;
```

## Requirements

| | |
|---|---|
| Runtime | .NET 10 |
| EF Core | 10.0 |
| Server-side provider | any — SQL Server, PostgreSQL, SQLite, InMemory … |
| Client platforms | anywhere .NET 10 runs, including Blazor WebAssembly |

**Authentication and authorization are out of scope and are yours.** No identity travels in
the envelope. Authenticate the transport, and use query filters on the *server's* model to
decide what a caller may see.
