# Trim-warning ratchet baseline — see eng/trim-ratchet.sh and the M8-17 entry in
# docs/plans/v10/implementation-plan.md.
#
# `ours` counts UNIQUE IL2xxx diagnostics whose declaring member is an InfoCarrier.Core type, from
# a `dotnet publish -c Release` of samples/Northwind.Client with PublishTrimmed=true.
#
# THE SPEC CRITERION IS NOT MET AND THIS FILE IS THE RECORD OF THAT. The Blazor sample design
# (docs/plans/v10/superpowers/2026-08-11-blazor-wasm-sample-design.md §9, criterion 4) asked for "no IL
# warning attributable to InfoCarrier.Core". There are 86. They are not sloppiness: the wire carries
# a type's NAME and the far end resolves it, so `Assembly.GetType(string)`, `MakeGenericMethod`,
# `MakeGenericType` and a reflective object walk are what this provider is made of.
# `[DynamicallyAccessedMembers]` cannot say "whatever type the caller's model names".
#
# THE APP RUNS TRIMMED ANYWAY. `PublishTrimmed=true` produces a working client -- M8-17 drove all
# three pages against the published output: queries, the projection split, both async navigation
# loads, a unit of work, and a committed transaction. These warnings mean the trimmer cannot PROVE
# the reflection is safe for an arbitrary model, not that it broke this one.
#
# 2026-08-16 (M8-17) — first measurement. 86 ours, 1129 total across all assemblies. The other
# 1043 are EF Core (864), Castle.Core (127), BCL (22), Fluent UI (11), the sample itself (8),
# ASP.NET Core (4) and a handful else; none of them is this repo's to fix, so only `ours` is gated.
# Distribution of ours by declaring type: DynamicValueMapper 12, NodeToExpressionTranslator 7,
# TransparentIdentifierRewriter 6, PrimitiveCoercion 5, TupleCarrier 5, ProjectionRewriter 5+2,
# TypeNodeResolver 3, QuerySplitter 3, ServerQueryExecutor 3, QueryExecutor 3+2, and the rest
# singletons. By cause: 45 are DynamicallyAccessedMembers mismatches (mostly `Type.GetInterfaces()`
# on a type the model named), 15 are MakeGenericMethod/MakeGenericType, 17 are IL2026 calls into
# APIs already marked RequiresUnreferencedCode.
# 2026-08-17 (M9, J8) — 86 -> 88, A DELIBERATE RISE OF 2, and the first change to this file since it
# was written. `WireGrouping.TryWrap` projects EF's internal grouping into this provider's own
# `WireGrouping<,>`, so that an EF internal type never has to be admitted to `TypeAllowlist`. It
# needs exactly the two things this file already names as the premise: `GetInterfaces()` on a runtime
# type (IL2075), and `MakeGenericType` from arguments the caller's model supplies (IL2062, through
# `Activator.CreateInstance`).
#
# IT WAS 5 AND IS 2, WHICH IS THE PART WORTH KEEPING. The first version filled the closed generic
# with `GetProperty`/`GetMethod` and cost three further warnings on the fill path alone. Filling it
# through a non-generic `IWireGroupingSink` that the closed type implements costs nothing: the closed
# type can cast to its own `IGrouping<TKey,TElement>`, and the caller never has to. So of the five,
# three were avoidable and were avoided; two are the premise and stay.
#
# A `[DynamicDependency]` on `TryWrap` keeps `WireGrouping<,>`'s parameterless constructor, which is
# reached only through `Activator.CreateInstance` and which a trimmer would otherwise be free to
# remove. That is a RUN-TIME correctness fix, not a warning fix, and it changes no count — without it
# a published client would fail on the first non-composed `GroupBy`, which is the class of break
# these warnings are about.
#
# `total` also falls, 1129 -> 853, and that is NOT this change: EF Core's own count dropped from 864
# to 585 with the package/SDK movement since M8-17. Recorded so the next reader does not read a
# 276-warning improvement as ours.
# 2026-08-24 — THIS FILE MEASURES TRIMMING AND SAYS NOTHING ABOUT NATIVE AOT. Recorded because the
# two were read as one axis until they were measured separately. A `PublishAot` publish of
# samples/Northwind.Demo reports 155 unique IL diagnostics, 153 of them ours, and 59 of those are
# IL3050 (RequiresDynamicCode) -- a code the trim analyzer NEVER emits, because trimming does not
# ask whether code can be GENERATED. So a third of the AOT picture is invisible here and always was.
# That publish did not finish either: it failed at the native link step for a missing platform
# linker, so no native binary has ever been produced or run. Native AOT is not a supported
# configuration for v10 (roadmap.md, M8 exit criteria); this ratchet is not the thing that would
# tell you if that changed. The two counts are NOT comparable and must not be subtracted: different
# samples, different tools (ILLink vs ILCompiler), different unique-keys.
#
# 2026-08-24 — `ours` unchanged at 88 after `UseInfoCarrier` gained [RequiresUnreferencedCode] and
# [RequiresDynamicCode]. Recorded because the opposite was expected. The attribute exempts only the
# annotated method's OWN body, and these 88 sit in methods EF reaches through its own interfaces,
# which `UseInfoCarrier` never calls. `total` rises 853 -> 854: the sample's call site now carries
# its own IL2026, acknowledged with a narrow pragma in Program.cs rather than hidden project-wide.
# 2026-08-24 — 88 -> 89, A DELIBERATE RISE OF ONE. `ServerQueryExecutor.ExecuteQueryAsync` now runs
# the server-side query through EF's async path so that the cancellation token reaching it from the
# transport is actually used (M5's last criterion, W6). The token was accepted and dropped: a client
# that cancelled stopped waiting while the server read the store to the end.
#
# Both paths need the query's own runtime type -- the element type for a sequence, the result type
# for a single result -- and only the caller's model knows it, so both dispatch through
# `MakeGenericMethod`. Both calls sit in one method, so they cost ONE unique diagnostic: IL2060 on
# `ExecuteQueryAsync`. This is the premise this file already describes, and there is no
# reflection-free shape available: `IInfoCarrierServer.QueryDataAsync` is non-generic by contract,
# because the wire cannot know the element type at compile time.
#
# The alternative was to poll the token between rows in the existing synchronous loop, which needs
# no reflection and costs no warning. It was rejected: it would stop this loop but not the store
# command, so the database would keep working for a client that had gone. That is the cost the fix
# exists to remove.
# 2026-09-02 (R120) — 89 -> 89, AND THE EXPECTATION THAT IT WOULD FALL WAS WRONG. Recorded because
# the reasoning behind the expectation is the kind that repeats. #97 deleted
# `RelationalQueryRootShape.cs`: 276 lines that resolved two EF relational expression types by full
# name, read four properties off them and called `Activator.CreateInstance` twice, under **ten
# `UnconditionalSuppressMessage` attributes**. Removing that much reflection was expected to lower
# `ours`.
#
# It could not have. Those ten attributes are SUPPRESSIONS: each one already kept its diagnostic out
# of this count, so the code contributed 0 to the 89 while it existed and contributes 0 now that it
# is gone. **Deleting suppressed reflection cannot lower a count that never included it.** The two
# measurements say so directly -- 89 with the file, 89 without it, and nothing else in the change
# touches the trimmer.
#
# THE WIN IS REAL AND THIS FILE IS THE WRONG PLACE TO LOOK FOR IT. What went away is ten written
# arguments that a trimmer could not check, replaced by two type names in
# `InfoCarrier.Core.Relational` that a compiler does. That package contributes **no IL diagnostic of
# its own** -- verified in the publish log, not assumed -- so `ours` is the same 89 spread over one
# fewer file.
#
# THE RULE: a suppression is not a warning. Count the suppressions separately if the goal is to
# remove unverifiable reflection, because this ratchet will report no progress on it.
# 2026-09-03 (R132) -- `ours` UNCHANGED at 89, `total` RISES 855 -> 1134, and the rise is NOT this
# product's. D3 is superseded (architecture.md section 6a, owner's decision): `InfoCarrier.Core` now
# references `Microsoft.EntityFrameworkCore.Relational`, so the Blazor publish ships that assembly
# and EF Core's own bucket goes 585 -> 864. Every one of those 279 diagnostics is EF's, in EF's
# code, and none of them is this repository's to fix -- which is exactly why only `ours` is gated
# and why this file has said so since it was written.
#
# THE PAYLOAD RISES ON PURPOSE AND IT WAS MEASURED FIRST: +0.62 MB brotli on this sample, 4.11 ->
# 4.73 MB, with the raw total 13.48 -> 15.77 MB. The cost is unconditional -- a build that
# references the assembly and calls nothing from it ships the identical figure, because the trimmer
# keeps it almost whole at 2.079 MB against 2.09 MB on disk. The decision weighed that against 262
# of 20,368 tests lost without it. **This file is not the place that decides it**; the supersession
# in `architecture.md` is, and it lists the three conditions that would reverse it.
# 2026-09-04 (R149) -- `ours` 89 -> 90, A DELIBERATE RISE OF ONE, and it is the same premise this
# file has described since it was written. The split-query hint now travels beside the tree on
# `QueryDataRequest.SplitQueryBehavior`, and `ServerQueryExecutor.ApplySplitQueryBehavior` re-applies
# it to the rebuilt query. `AsSplitQuery<TEntity>` is generic and the element type is whatever the
# caller's model named, so the call dispatches through `MakeGenericMethod`: IL2060, one unique
# diagnostic, in a method that already sits beside two others of exactly this shape.
#
# TWO OF THE THREE WARNINGS IT FIRST COST WERE AVOIDABLE AND WERE AVOIDED, which is the part worth
# keeping. The first version looked the methods up with `GetMethod(name)`, invisible to the trimmer
# and worth two IL2xxx on its own; taking them from a delegate over the method instead is an
# ordinary reference the trimmer sees and says nothing about. The second version added its own
# `Type.GetInterfaces()` walker and cost an IL2070; reusing this class's existing `GetElementType`,
# already counted here, costs nothing. So of three, two were avoidable and one is the premise.
#
# `total` is unchanged at 1134. It buys eight specification tests: SQLite refuses `APPLY`, and a
# real split query never asks for it.
